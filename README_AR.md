# مسار — تطبيق مستقل لإدارة فرص سوائل الحفر

هذه النسخة React + TypeScript + Vite، مع Supabase Auth وPostgreSQL. لا تستخدم OpenAI أو ChatGPT للدخول أو للحفظ أو لتوليد الرسائل. الرسائل تُولَّد بقوالب محلية، ولا تُرسل بياناتها إلى نموذج ذكاء اصطناعي.

## حالة التسليم وحدود التحقق

- الكود كامل وقابل للنشر خارج Sites، بلا ملفات تشغيل خاصة بـ OpenAI.
- البناء وفحص TypeScript ناجحان. اختبارات الحقول، التواريخ والمتابعة ناجحة.
- اختُبر SQL الفعلي محليًا باستخدام PGlite، بما يشمل إنشاء السجل وتعديله واسترجاعه بعد إغلاق قاعدة البيانات وفتحها، وحذفه، وعزل حسابين ورفض الوصول المجهول.
- هذه الاختبارات لا تعني أن مشروع Supabase مستضافًا قد أُنشئ لك. لم تُقدَّم إعدادات مشروع تملكه، لذلك اتصال Supabase المستضاف والدخول الفعلي والبريد والنشر على نطاقك لم تُختبر بعد.
- عند عدم تهيئة Supabase، يعرض التطبيق شاشة إعداد ويتوقف؛ لا يتحول خفيةً إلى بيانات وهمية أو تخزين محلي.

## البنية والحفظ

المتصفح → Supabase Auth بالبريد وكلمة المرور → Supabase Data API → جدول PostgreSQL باسم `public.career_jobs`.

كل صف له `user_id` مرتبط بحساب الدخول. تفرض PostgreSQL سياسات RLS للقراءة والإضافة والتحديث والحذف حسب صاحب الصف. ليس إخفاء الأزرار هو الذي يحمي البيانات.

السجلات لا تُحفظ في `localStorage` أو `sessionStorage`. تُستخدم `sessionStorage` لجلسة الدخول فقط؛ تحديث الصفحة يحتفظ بالجلسة عادة، وإغلاق التبويب قد يتطلب دخولًا جديدًا، لكن السجلات تبقى في قاعدة البيانات. يمكنك الدخول من جهاز آخر وقراءتها.

نجاح الحفظ لا يظهر إلا بعد إقرار قاعدة البيانات. تعطل الشبكة أو رفض الصلاحيات يعرض خطأ. لا يُضمن حفظ تعديل لم تظهر له رسالة نجاح. الاستيراد ينفذ upsert واحدًا لكل ملف (حتى 500 سجل) بدل سلسلة حفظ جزئي.

الحفظ المستمر ليس بديلًا عن النسخ الاحتياطية: استخدم تصدير JSON دوريًا، وراجع سياسة الاحتفاظ والنسخ الاحتياطية لخطة Supabase التي تختارها. الملفات المصدّرة غير مشفرة تلقائيًا.

## الإعداد الأول — في حسابك الخاص

1. أنشئ مشروعًا في [Supabase](https://supabase.com/dashboard). اختر المنطقة المناسبة لاحتياجاتك.
2. افتح SQL Editor وشغّل `supabase/schema.sql` مرة واحدة في قاعدة جديدة. الملف لا يحذف جداول أو بيانات موجودة. إن كان الجدول موجودًا، راجعه قبل أي تغيير؛ لا تعالج الخطأ بحذف البيانات.
3. من Authentication فعّل البريد وكلمة المرور. أنشئ حسابك من لوحة المستخدمين بكلمة مرور قوية أو بدعوة إلى بريدك. عطّل التسجيل العام إذا أردت تطبيقًا شخصيًا فقط. لا يوجد نموذج تسجيل عام في التطبيق.
4. انسخ Project URL وPublishable Key. مفتاح `anon` القديم مدعوم أيضًا. **لا تستخدم `service_role` أو `sb_secret_` في الواجهة أو متغيرات VITE.**
5. انسخ `.env.example` إلى `.env.local` واكتب الإعدادين:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
```

هذه إعدادات عميل عامة، وليست كلمة مرورك أو صلاحية إدارية. حمايتها تعتمد على RLS والمصادقة. لا تُرسل كلمة مرور Supabase أو مفاتيح الإدارة إلى أي محادثة، ولا تضف `.env.local` إلى Git.

6. لاستعادة كلمة المرور: اضبط Site URL على رابط النشر النهائي وأضف `https://YOUR_DOMAIN/?recovery=1` إلى Redirect URLs. أضف رابط التطوير المحلي عند الحاجة. راجع إعداد SMTP وحدود إرسال البريد في مشروعك. التطبيق يضم مسار طلب استعادة ثم تعيين كلمة مرور جديدة؛ اختبار وصول البريد يحتاج مشروعك الفعلي.
7. ثبت Node.js 22.13 أو أحدث:

```bash
npm ci
npm run dev
```

يفتح Vite رابط التطوير الظاهر في الطرفية. لا تستخدم بيانات حساسة قبل إكمال اختبار القبول على مشروعك.

## النشر على Vercel

1. ضع محتويات مجلد `standalone` في مستودع Git تملكه، ثم استورده في Vercel. أو اجعل Root Directory هو `standalone` إذا رفعت الحزمة كاملة.
2. Framework: Vite. Build: `npm run build`. Output: `dist`. نسخة Node: 22.
3. أضف متغيري VITE أعلاه في إعدادات المشروع ثم انشر. هذه المتغيرات تُدمج أثناء البناء، فتغييرها يحتاج إعادة نشر.
4. أضف نطاقك من إعدادات Domains واتبع سجلات DNS التي تعرضها Vercel، ثم حدّث Site URL وRedirect URLs في Supabase.
5. ملف `vercel.json` مرفق لإعادة التوجيه ورؤوس الأمان. لا توجد وظائف Serverless أو حاجة لقاعدة SQLite محلية على Vercel.

## النشر على Netlify أو استضافة ثابتة أخرى

- على Netlify: Build command `npm run build`، Publish directory `dist`، ومتغيرا VITE في إعدادات البناء. `netlify.toml` و`public/_redirects` و`public/_headers` مرفقة.
- يمكن بناء `dist` محليًا بالإعدادات الصحيحة ثم رفع محتواه إلى استضافة تدعم HTTPS. قاعدة البيانات تبقى في مشروع Supabase وتعمل مستقلّة عن مكان استضافة الواجهة.
- إذا استخدمت نطاقًا مخصصًا لخادم Supabase نفسه، عدّل `connect-src` في `vercel.json` و`public/_headers` ليشمل أصله؛ الافتراضي يسمح بنطاقات `*.supabase.co`.
- ملفات JavaScript والواجهة تكون عامة على الاستضافة، لكن سجلاتك لا تُضمَّن في ملفات البناء؛ تبقى خلف Supabase Auth وRLS. لا تُدرج سجلاتك الخاصة في ملفات `public`.
- تملك الكود وحساب الاستضافة ومشروع البيانات. هذا استقلال عن OpenAI، مع اعتماد تشغيلي واضح على مزودي الاستضافة وSupabase. الاستضافة الذاتية الكاملة لـ Supabase ممكنة لكنها مهمة بنية تحتية منفصلة عن هذه الحزمة.

## نقل السجلات من الموقع القديم

1. سجل الدخول إلى موقع Sites القديم، واختر «تصدير» للحصول على JSON. لا تحذف النسخة القديمة قبل التأكد من النقل.
2. جهّز النسخة المستقلة وسجّل الدخول بحساب Supabase الخاص بك.
3. اختر «استيراد نسخة سابقة» أو «استيراد»، وحدد JSON. راجع عدد السجلات وقارن عينات من كل الحقول، ثم حدّث الصفحة وسجّل الخروج والدخول مجددًا للتحقق.
4. إن لم تتمكن من دخول النسخة القديمة، لا تتجاوز حمايتها. استعادة بيانات D1 تحتاج وصولًا مخولًا إلى حساب الاستضافة/المشروع؛ الكود المصدري لا يحتوي على سجلات قاعدة البيانات.

هذه النسخة لا تعبئ سجلات التقديمات السابقة داخل JavaScript المنشور. هذا يحمي تفاصيل طلباتك من الظهور في ملفات الواجهة العامة. لا توجد وظائف مزعومة مفتوحة أو درجات ملاءمة مصطنعة.

## الحقول المطلوبة

القائمة التفصيلية في `FIELD_AUDIT_AR.md`. جميع الحقول الأصلية محفوظة: الشركة، المسمى، الدولة والمدينة، الرابط، تاريخ النشر والتقديم، الحالة، رقم الطلب ورسالة التأكيد، آخر متابعة والتالية، الرعاية، التناوب، السكن، التذاكر، درجة الملاءمة، الفجوات والمتطلبات، حالة التحقق وتاريخه وملاحظاته. أضيفت إعدادات نافذة المتابعة وعطلة الأسبوع وتاريخ المراجعة الأسبوعية.

التفاصيل الموسعة تظهر عند «إضافة فرصة» أو الضغط على اسم الشركة/زر التعديل. الجدول يعرض ملخصًا لتقليل ازدحام الشاشة. درجة الملاءمة تقييم يدوي، والتحقق من الإعلان يدوي. لا اتصال آلي بالشركات أو البريد.

## منطق المتابعة والملف المهني

- تتطلب رسالة المتابعة تاريخ تقديم ورقم طلب أو نص تأكيد وحالة طلب نشطة.
- اختر قالب 5–7 أو 7–10 أيام عمل. يُحسب من التقديم أو آخر متابعة، مع استبعاد الجمعة/السبت أو السبت/الأحد وفق اختيارك. العطلات الرسمية تحتاج تعديل الموعد يدويًا.
- موعد يدوي أبكر لا يتجاوز شرط الانتظار؛ موعد لاحق يؤجل الأهلية.
- الرسائل قابلة للتحرير والنسخ، ولا تُرسل تلقائيًا. «تسجيل متابعة أرسلتها» يُستخدم بعد الإرسال الفعلي فقط.
- الخبرة الميدانية تُعرض باعتبارها معلومات قدّمها المستخدم؛ التدريب والاعتمادات تُفصل عنها. MPD بصيغة `training/awareness` فقط. لا تضاف شهادة IWCF أو كفاءة تشغيل MPD إلى الرسائل افتراضًا.

## الاختبارات

```bash
npm test
npm run test:database
npm run build
```

اختبار Supabase المستضاف متاح بعد الإعداد: أنشئ حسابي اختبار مؤقتين في مشروعك. أضف متغيرات **غير مسبوقة بـ VITE** إلى `.env.local`:

```dotenv
MASAR_TEST_EMAIL_A=YOUR_TEST_USER_A
MASAR_TEST_PASSWORD_A=YOUR_TEST_PASSWORD_A
MASAR_TEST_EMAIL_B=YOUR_TEST_USER_B
MASAR_TEST_PASSWORD_B=YOUR_TEST_PASSWORD_B
```

ثم:

```bash
npm run test:live
```

الاختبار يضيف سجلًا موسومًا بوضوح للاختبار، يعدله، يعيد قراءته من جلسة جديدة، ويختبر منع حساب آخر من قراءته أو تعديله أو تزوير مالكه، ثم ينظف سجل الاختبار. ينشئ تقريرًا محليًا `verification-results.json` دون كلمات مرور. لا تستخدم حسابات أشخاص آخرين ولا مفاتيح الإدارة لهذا الاختبار. الاختبار لا يفحص تسليم بريد الاستعادة أو DNS؛ اختبرهما يدويًا.

للقبول النهائي عبر الواجهة: أضف فرصة اختبار بكل الحقول، احفظها، أعد تحميل الصفحة، سجّل الخروج والدخول، افتحها من جهاز آخر، عدّلها، وصدّرها واستوردها. تحقق من أن رسالة متابعة غير مؤكدة لا تتولد، وأن الحقول الحساسة لا تُقرأ عند تسجيل الخروج.

## مكونات الحزمة

- `src/Auth.tsx`: دخول واستعادة كلمة المرور.
- `src/Dashboard.tsx`: الواجهة العربية وإدارة الفرص والفلاتر والمقارنة والرسائل.
- `src/storage.ts`: القراءة والحفظ والاستيراد والحذف في Supabase.
- `src/fields.ts`: تحقق الحقول والتحويل إلى أعمدة PostgreSQL.
- `src/logic.ts`: أيام العمل وأهلية المتابعة.
- `supabase/schema.sql`: قاعدة البيانات والقيود وصلاحيات RLS.
- `tests/`: اختبارات الحقول والمنطق وقاعدة البيانات.
- `scripts/verify-live.ts`: اختبار قبول اختياري لمشروعك المستضاف.
